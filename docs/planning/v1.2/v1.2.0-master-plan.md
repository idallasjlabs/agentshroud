## Why v1.2.0

After v1.1.1 ("Hermes" multi-bot release) and the maintenance train of PRs #141/#157–167/#190/#191, the next minor opens up **five independent capability bets** that can be developed in parallel and shipped together. Each bet has a champion module set, an existing module surface to extend (no greenfield work), and a clear acceptance test.

The five bets, organized as workstreams below:

| # | Workstream | One-line ask |
|---|------------|----|
| **A** | Groups & Teamwork in OpenClaw | Move OpenClaw from single-collaborator → multi-collaborator/team sessions with isolation per group |
| **B** | Security features from competitive intel | Extend the 26-module security matrix with the next-tier features competitors are starting to surface |
| **C** | Full local-model parity for both bots | OpenClaw + Hermes both fully functional on local LLMs (LM Studio / Ollama / mlx_lm), no cloud dependency for any flow |
| **D** | Sync agents/skills/MCP from `~/.llm_settings` into both bots | Make the personal-laptop LLM-settings tree the source-of-truth for what skills/MCP the production bots run |
| **E** | Blue + red team security scan, both bots | Run the full assessment suite against OpenClaw + Hermes; address every finding |

All five gate to the same v1.2.0 ship. Each workstream owns its own feature branches and PRs; this plan is the cross-workstream index.

## Workstream A — Groups & Teamwork in OpenClaw

### Intent

Today OpenClaw exposes a single 1:1 collaborator surface (Telegram DM → per-`telegram_uid` workspace under `.agentshroud/collab-{uid}/`). Memory: "Per-Collaborator Memory Isolation — Agent ID: `collab-{telegram_uid}`; Workspace: `.agentshroud/collab-{uid}/` on `agentshroud-config` volume." The new ask is **groups**: a Telegram group / Slack channel becomes a first-class team-workspace where OpenClaw maintains shared memory, threaded approvals, and per-member ACL.

### Acceptance

- A Telegram group with N members maps to one shared workspace `.agentshroud/group-{chat_id}/` with isolated memory from any member's DM workspace
- Approval routing: high-risk actions in a group context page the **owner** (not whichever group member triggered)
- Per-member RBAC: OpenClaw maps Telegram user IDs in the group to a roles map (owner / member / read-only)
- All existing P1 modules (ConsentFramework, SessionManager, AgentRegistry, Delegation, SharedMemory, ToolACL) treat the group as a first-class agent identity

### Module surface to extend

| Module | File:area | Change |
|--------|-----------|--------|
| AgentRegistry | `gateway/security/agent_registry.py` | Register `group-{chat_id}` identities alongside `collab-{uid}` |
| SharedMemory | `gateway/security/shared_memory.py` | Per-group workspace namespace + cross-member isolation |
| ConsentFramework | `gateway/security/consent_framework.py` | Group-context consent acknowledgement (one consent covers all members) |
| ToolACLEnforcer | `gateway/security/tool_acl.py` | Per-member role lookup before approving tool calls in group context |
| TelegramAPIProxy | `gateway/proxy/telegram_proxy.py` | Detect group `chat.type=='group'|'supergroup'`, set group-context contextvar (parallels existing `_inbound_bot_id`) |
| ApprovalQueue | `gateway/approval_queue/` | Group-aware routing: approval messages reply in the group thread, owner gets DM mirror |
| openclaw apply-patches.js | `docker/config/openclaw/apply-patches.js` | `dmPolicy.allowFrom` extension for group chat IDs |

### Out of scope

- Slack groups deferred to v1.3 (Telegram only for v1.2)
- Voice/video channels deferred (text only)

### Tests to add

- `gateway/tests/test_group_isolation.py` — memory writes in group A invisible from group B and from any DM workspace
- `gateway/tests/test_group_approval_routing.py` — owner gets DM mirror for group-context approvals
- `gateway/tests/test_group_rbac.py` — read-only member cannot trigger high-risk tool calls

## Workstream B — Security features from competitive intel

### Source of truth

- `docs/security/competitive-security-matrix.md` — 26-module matrix, current AgentShroud score `26/26 (100%)`, lead over closest competitor (Zetherion `4/26`) is 22 modules
- `docs/security/competitive-analysis-reports-archive.md` — index of historic reports
- Hermes cron-generated competitive intel emails (per `docker/config/openclaw/cron/jobs.json` + `docker/config/hermes/cron/jobs.json` — twice daily, 06:00 + 15:00 local)

The matrix says we're feature-complete vs every competitor today. The competitive thesis for v1.2.0 is therefore **extend lead, not catch up.** Two sub-tracks:

### B.1 — Lock the lead: 26+ modules

The competitive matrix highlights "8 deep hardening modules that address attack vectors no other platform has even identified." Item-by-item review needed against the latest competitive reports to identify the next 2–3 capabilities to add. Candidate sources for new modules:

- **MCP tool-call provenance signing** — extend SHA-256 audit chain to per-tool-invocation envelope signing (a different surface than the current pipeline-level chain)
- **Cross-bot trust ledger** — `trust_manager.py` already has per-agent state; expose a shared decay function so an OpenClaw incident demotes Hermes's effective trust in the same pipeline run
- **Differential PII detection on tool RESULTS vs prompts** — current PII confidence floor is 0.9 (memory rule). A lower-floor pass on incoming tool results (where false positives are tolerable) catches model-injected exfil that's adversarially formatted to defeat the prompt-side filter
- **Hermes / OpenClaw cross-channel consistency check** — same query through both bots should not produce divergent egress targets; divergence = compromise signal

### B.2 — Strengthen the report pipeline itself

The Hermes-generated competitive intel report is currently best-effort markdown sent via email. Hardening it:

- Schema-validate every generated report against a Pydantic model so downstream automation (this plan's Workstream B.1) can consume it programmatically
- Store reports in `gateway-data` volume with hash-chain integrity per the existing audit chain pattern
- Add `gateway/web/api.py` endpoint `/api/intel/competitive` exposing latest report (auth-gated, owner-only)

### Acceptance

- 2–3 new modules in the pipeline with full test coverage
- Competitive-intel reports are Pydantic-validated, hash-chained, and surfaced in the dashboard
- Competitive matrix updated to reflect 28+ modules, new gap analysis

### Tests to add

- One unit-test file per new module (TDD per CLAUDE.md §4)
- `gateway/tests/test_intel_pipeline.py` — schema validation + hash chain integrity for cron-generated reports

## Workstream C — Full local-model parity for both bots

### Source of truth

- `docs/planning/v1.2/LOCAL_LLM_REVIEW.md` (already in planning) — the design baseline
- Memory: "Multi-model defaults: Anchor `qwen3.5:27b` · Coding `qwen2.5-coder:32b` · Reasoning `deepseek-r1` (→ mlx_lm)"
- Memory: "`scripts/switch_model.sh local [model] [--wait]`"
- Memory: "Failover Model-Ref Normalization — `AGENTSHROUD_LOCAL_MODEL_REF=ollama/qwen3:14b` becomes `qwen3-14b` when the failover dispatch hits LM Studio. Gateway normalizes via `gateway/proxy/llm_proxy.py::_normalize_local_model` (PR #171)."

### Intent

Today OpenClaw is "cloud mode" by default (per memory: `AGENTSHROUD_MODEL_MODE=cloud`, `anthropic/claude-opus-4-6`). Hermes is cloud-first too. v1.2.0 makes either bot runnable **end-to-end on local-only models** with no degradation:

- Full tool-use (the local model can call all OpenClaw + Hermes tools as cleanly as Claude)
- Full failover chain (local primary → local secondary → emergency cloud)
- All scheduled crons run on local without quota concerns
- Telegram-facing latency stays within 2× of cloud mode

### Surface to extend

| Component | File:area | Change |
|-----------|-----------|--------|
| llm_proxy normalization | `gateway/proxy/llm_proxy.py::_normalize_local_model` | Round-trip every model-ref through normalization; add LM Studio + Ollama + mlx_lm dispatchers |
| Local model anchor config | `docker/config/openclaw/AGENTS.md` (per memory: "qwen3-14b ignores tool rules in SOUL.md; must be in AGENTS.md with examples") | Local-model-specific tool-use prompt blocks |
| Switch script | `scripts/switch_model.sh` | Atomic switch all bots together; verify ready before flipping (currently has `--wait`) |
| Hermes failover | `docker/bots/hermes/...` | Mirror OpenClaw's local-first dispatch; ensure DuckDuckGo + Yahoo/Google/Mojeek/Yandex search engines (added in PR #190) are reachable in local mode |
| Failover heuristic | `gateway/proxy/llm_proxy.py` | Memory: "PR #180: trigger cloud→local on persistent 429 (rate-limit, not quota)" — extend to local→local-secondary on local OOM / >30s p99 |
| Resource Guard config | `gateway/security/resource_guard.py` | Pre-flight check for local-model VRAM headroom before dispatching long-context calls |

### Acceptance

- Both bots can run a full week on local-only models with zero owner intervention
- `scripts/switch_model.sh local qwen3.5:27b --wait` flips both bots and both pass smoke + post-deploy-check
- All scheduled crons (kaizen, chaos drill, daily memory journal, weekly stability, competitive intel AM/PM) complete on local without quota failures

### Tests to add

- `gateway/tests/test_llm_proxy_local_parity.py` — every cloud-mode tool call has a local-mode equivalent that returns equivalent shape
- `gateway/tests/test_switch_model_idempotent.py` — running `switch_model.sh local <m>` twice is a no-op the second time

## Workstream D — Sync agents/skills/MCP from `~/.llm_settings` into both bots

### Intent

The owner's personal-laptop LLM tree (`~/.llm_settings/` or wherever the canonical skills/agents/MCP definitions live) drifts from what's deployed into OpenClaw and Hermes container images. v1.2.0 establishes a single source of truth + a deterministic sync.

### Open question (planning-only — decide before coding)

The owner has used "`llm settings`" loosely in conversation; the actual path is one of `~/.llm_settings/`, `~/.claude/skills/`, or a separate Git repo. **Decide before workstream D starts: which directory is canonical, and what's the sync mechanism (`rsync`, git submodule, build-time `COPY`, runtime mount)?**

### Surface to extend

| Component | Change |
|-----------|--------|
| Build scripts | `docker/bots/{openclaw,hermes}/Dockerfile` — `COPY` skills/agents/MCP definitions from canonical path during build |
| Or runtime mount | `docker/docker-compose.yml` — `volumes:` entry mapping the canonical path read-only into bot containers |
| Manifest validation | New file `scripts/validate-skills-manifest.sh` — compare deployed manifest against canonical; fail CI if drift |
| Settings hot-reload | `gateway/web/api.py` — `/api/skills/reload` endpoint (auth-gated) to re-read manifest without container restart |

### Acceptance

- Single command (`scripts/sync-llm-settings.sh`) brings both bots into sync with the canonical tree
- CI gate fails if the canonical tree changes without a corresponding rebuild
- Owner can add a skill on the laptop → next deploy includes it in both bots automatically

### Tests to add

- `gateway/tests/test_skills_manifest_sync.py` — deployed manifest matches canonical hash
- Shell smoke test under `scripts/smoke.d/` — sync script is idempotent

## Workstream E — Blue + red team security scan, both bots

### Source of truth

- Historic redteam plans + assessments — see `docs/planning/redteam/` (moved this PR), particularly `plan.md` and `v0.7.0-remediation-plan.md`
- Blue-team audits — `docs/planning/v0.8/blue-team-assessment-v0.8.0*.md` (moved this PR), plus older `docs/planning/reviews/blue-team-audit-v0.7.0.md`
- Memory: "Coverage: ≥ 94% on new or modified code (AgentShroud floor)"
- Per CLAUDE.md §2 — "No Security Theater" rules apply

### Intent

The historic red-team passes (v0.7, v0.8) focused on OpenClaw + the gateway. Hermes was added in v1.1 and has not had a parallel pass. v1.2.0 brings both bots to **equivalent assurance state**, with findings tracked through to fix-or-accept.

### Phases

**E.1 — Blue team audit (defensive posture inventory)**
- Re-run the v0.8.0 blue-team checklist (`docs/planning/v0.8/blue-team-assessment-v0.8.0-final.md`) against current main
- Add a Hermes-specific section: per-bot egress allowlist completeness, per-bot trust seeding, per-bot CVE triage cron health
- Output: `docs/planning/v1.2/blue-team-assessment-v1.2.0.md` + findings spreadsheet

**E.2 — Red team simulated attack run**
- Re-run the v0.7.0 red-team scenarios (`docs/planning/redteam/*`) against both bots
- Add new scenarios for the v1.1 multi-bot attack surface: cross-bot trust pivot, shared-memory leak between bots, group-context escalation (which Workstream A introduces)
- Output: `docs/planning/v1.2/red-team-assessment-v1.2.0.md` + per-finding remediation issue

**E.3 — Fix or accept, every finding**
- Per CLAUDE.md §0, every accepted-risk needs a tracked rationale
- No "deferred to v1.3" finds without an owner-signed acceptance

### Acceptance

- Both bots pass the v1.2.0 blue-team checklist (≥ same coverage as v0.8.0 had for OpenClaw)
- Every red-team finding is either fixed-and-tested-in-PR or signed-off-and-tracked
- `scripts/security-scan.sh` exit code 0 on the v1.2.0 release commit

### Tests to add

- One regression test per fixed finding (TDD-style — finding becomes the failing test, fix makes it pass)
