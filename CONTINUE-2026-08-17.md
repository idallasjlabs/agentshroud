Diagnostic evidence gathered (before restoring the job's original prompt):
- `docker logs agentshroud-hermes-v2` showed **zero non-heartbeat log lines**
  during the entire stall window — no tool-call attempt, no error, no
  exception.
- `docker logs searxng-local` showed **zero incoming requests** during the
  stall — the stall is NOT a hung web-search network call.
- `tail /tmp/local-llms/omlx.log` showed **zero new chat-completion requests**
  for this job during the stall (the only omlx activity in that window
  belonged to the concurrently-running OpenClaw CVE-triage job, and even after
  that job's request finished/aborted and freed omlx up, the Hermes job stayed
  stalled) — the stall is NOT the model queued behind a busy server either.
- The `hermes cron run` process itself was alive (`ps aux` showed 0.5-0.9%
  CPU, not zero) — not a hard deadlock, but making no externally-visible
  progress.
- **py-spy is NOT usable *inside* `agentshroud-hermes-v2`** — unlike gateway
  (see `[[feedback_pyspy_gateway_diagnosis]]`), this container's seccomp
  profile does not include `ptrace` in its allowed-syscall list, so `py-spy
  dump` run via `docker exec` fails with `Permission denied` even as root.
  **Workaround found and used successfully: run py-spy from the Colima VM
  itself** (`colima ssh`), targeting the container's *host-level* PID (from
  `docker top agentshroud-hermes-v2`, NOT the container-internal PID from
  `docker exec ... ps aux` — these are different numbers, the container has
  its own PID namespace). A host-level tracer isn't subject to the
  container's seccomp filter. Static py-spy binaries aren't published for
  Linux (only wheels) — extract the binary from the manylinux aarch64 wheel
  with Python's `zipfile` module (no `unzip` on the VM):
  `py_spy-0.4.2.data/scripts/py-spy` inside
  `py_spy-0.4.2-py2.py3-none-manylinux_2_17_aarch64.manylinux2014_aarch64.whl`.
  strace works the same way (`sudo apt-get install -y strace` on the VM,
  Ubuntu 24.04 aarch64) for non-Python processes (used this for OpenClaw's
  Node.js gateway, where py-spy doesn't apply — "Failed to find python
  version from target process").

**ROOT CAUSE FOUND 2026-08-17 (later in the same day) — resolved the "genuine
hang" conclusion above.** It was never a hang in Hermes's own agent loop.
Live py-spy dumps (via the VM workaround) on both the `hermes cron run`
process AND the `agentshroud-gateway` process at the same moment showed:
- Hermes's MainThread genuinely blocked waiting on
  `"waiting for non-streaming API response"` from `http://gateway:8080/v1`.
- The gateway's own executor thread (confirming `[[project_gateway_hang_scrum154]]`'s
  fix is intact — the blocking `urlopen`+`read()` correctly runs off the event
  loop, so the gateway's OWN health endpoint stayed responsive throughout)
  genuinely blocked in `http/client.py:478 read()` → `_read_chunked` →
  `readinto(socket.py)`, i.e. waiting on real bytes from omlx.
- Cross-referencing `/tmp/local-llms/omlx.log`: the model **was** generating
  the whole time — omlx only logs a `Chat completion: N tokens in Ns` line
  once a generation finishes, so "zero new omlx log lines" during a stall
  is NOT evidence of no activity, it's exactly what an in-progress
  multi-minute generation looks like from the log's perspective. This
  invalidated the earlier "zero omlx activity ⇒ not queued behind the model"
  conclusion above — that reasoning was wrong.
- The actual failure mode: `hermes config get model` showed
  `temperature: 0` (fully deterministic/greedy decoding) and
  `max_tokens: 24576`. Confirmed via omlx.log: multiple completions hit
  **exactly 24576 tokens** (`Chat completion: 24576 tokens in 2010.23s
  (12.2 tok/s)`) — the model was stuck in a runaway repetition loop with no
  sampling randomness to escape it, burning the full token budget at
  ~12 tok/s before the connection returned **33+ minutes later**. That is
  the "indefinite hang" — Hermes wasn't broken, it was faithfully waiting on
  a legitimately-still-running (but degenerate) 33-minute generation.
  `cron.max_tokens: 8192` exists in `config.yaml` as an apparently-intended
  cron-specific ceiling but is NOT applied to this job's actual code path
  (`_current_provider: "custom"` via the gateway, not the `"ollama"` path
  `cron.max_tokens` seems scoped to) — flagged as a separate, unconfirmed
  vendor-config quirk, not fixed (no per-job `--max-tokens` CLI override
  exists on `hermes cron edit`).

**Fix applied (partial success, NOT fully resolved):**
`hermes config set model.temperature 0.2` (was `0` — greedy decoding is the
classic cause of exact-repetition runaway generation in small quantized
models; a small nonzero temperature is the standard mitigation) and
progressively `hermes config set model.max_tokens` `24576 → 8192 → 3072`
(bounds worst-case damage; 8192 matches what `cron.max_tokens` already
intended). **Confirmed via omlx.log that the tighter ceiling took effect**
(a later runaway capped at exactly 8192 tokens instead of 24576, ~1195s
instead of ~2010s) — **but `temperature: 0.2` alone did NOT eliminate the
runaway tendency**, it recurred at least twice post-fix, just failing faster
each time. This is a real, verified improvement (worst case bounded to
minutes instead of 20-33 minutes) but not a complete fix. Current committed
config: `temperature: 0.2`, `max_tokens: 3072` (global `model.*`, affects
all Hermes usage, not just cron — 3072 tokens is still generous for any
single interactive reply).

Fallback steps 2 and 3 from the original list are now MOOT (superseded by
the above) — the stall was never about max_tokens being wrong for the task,
it was about the model never naturally stopping. **Next steps if picked back
up:** (a) try a higher temperature (0.4-0.7) or an explicit repetition
penalty if Hermes/omlx exposes one via config — temperature 0.2 wasn't
enough entropy; (b) still consider dropping from 4 searches to 3 per section
(original fallback #3) — a shorter prompt reduces the surface for the model
to enter a degenerate loop in the first place, independent of sampling
settings; (c) investigate why `cron.max_tokens: 8192` isn't applied to
`custom`/gateway-routed jobs — fixing that properly (rather than lowering
the global default) would avoid affecting non-cron Hermes usage.
