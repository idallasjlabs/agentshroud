## 1. Bugs found and fixed in the Sunday-upgrade tooling itself

The deterministic script (`scripts/sunday-upgrade-apply.sh`) had never
actually been run to completion on this account before. It had three real
bugs, all fixed and committed on `chore/upgrade-2026-09-14`:

1. **Hardcoded the broken `docker compose` plugin form.** This host only has
   a working standalone `docker-compose` binary (same defect
   `scripts/update-agentshroud.sh` already documents/works around) — every
   phase failed outright (`preflight` exit 10, "compose file is invalid").
   Fixed to resolve the compose command via `scripts/lib/container-runtime.sh`,
   same as `scripts/asb` already does.
2. **Never applied the per-account compose override.** Only ever pointed at
   the base `docker-compose.yml`, missing
   `docker-compose.agentshroud-bot.marvin.yml`, which renames containers
   (`agentshroud-gateway` → `agentshroud-marvin-gateway` on this host). Every
   phase would have inspected/built against containers that don't exist
   under this account. Fixed the same way as (1) — now resolves engine +
   override file + project name like `asb` does. Documented that
   `SUNDAY_CONTAINERS` must still be passed explicitly per bot-host (the
   container-name suffix isn't always the bare hostname — `raspberrypi` →
   `rpi`, confirmed while checking the other two dev hosts).
3. **Phantom `:latest` scan tag** — `DEFAULT_SCAN_IMAGES` hardcoded `:latest`,
   but images are tagged by `AGENTSHROUD_VERSION` (e.g. `agentshroud-gateway:1.6.0`).
   `:latest` is never pushed, so the CVE gate silently scanned nothing and
   reported a false "0 CRITICAL" pass. Independent copy of the exact defect
   already fixed in the daily CVE scan itself (PR #442). Fixed to derive the
   tag from `AGENTSHROUD_VERSION`.
4. **Never activated the compose profiles that gate `hermes`/`voice-gateway`.**
   Both are `profiles: [hermes|voice, full]` in `docker-compose.yml` — without
   an explicit `--profile` flag, `docker compose config/build/up` silently
   excludes both. The very first successful-looking apply run today built and
   "recreated" only 3 of 5 required containers and still reported PASS.
5. **`hermes`'s container isn't compose-managed at all.** Even after fixing
   (4), `docker compose up` still can't bring `hermes` up correctly: its
   container lifecycle is owned by `scripts/asb`/`docker/bots/hermes/run-standalone.sh`,
   which resolves secrets from `$HOME/.agentshroud/.asb-secrets` — a mechanism
   plain `docker compose up` knows nothing about. This one caused a real
   incident during the run; see §4 below. Fixed by excluding `hermes` from
   both `up -d` and the generated `rollback.sh`, and deploying it separately
   via `scripts/asb up hermes` (the tested, working path) when it was rebuilt.

All five are genuine, previously-unexercised bugs in a script whose own header
already documents three prior failed runs (2026-09-06, -09, -11) — this is
the first time it has ever completed a real `apply` → `verify` cycle on this
account.

### 4.1 OpenClaw 2026.9.4 — BLOCKED, root cause fully diagnosed

`scripts/check-vendor-compat.sh`'s schema-validation gate fails:
`openclaw config validate --json` produces **no output at all** except a
runtime warning and exits 1 — for *every* invocation, including
`--help`, regardless of config content. This is not a schema-content
rejection; the command itself crashes.

Root cause: the warning names it directly —
`openclaw: Node 22.23.2: node:sqlite truncates TEXT at embedded NUL
(nodejs/node#61954); use 24.16+/26.1+ or a build with the fix`. OpenClaw
2026.9.4 apparently now touches `node:sqlite` from the `config validate`
path, which trips a known Node 22.23.2 bug. Our image is pinned to
`node:22-bookworm-slim`.

**Why this stays BLOCKED rather than force-fixed today:** the fix is a
*base Node major-version bump* (22 → 24.16+/26.1+) for the whole OpenClaw
image — a materially different class of change from a leaf CVE patch or a
patch-anchor re-sync. It has broad blast radius (native module ABI,
memory/perf characteristics) and this repo has recent, direct precedent for
that kind of base-image jump going wrong under time pressure (`chore/upgrade-2026-09-06`'s
reverted voice-gateway bookworm rebase). It deserves its own dedicated
verification pass, not one done inside an already-long multi-component cycle.
OpenClaw stays pinned at `2026.7.1-2`.

### 4.2 Hermes v0.20.6 — BLOCKED after two real fixes landed

Two independent, genuine compat breaks were found, root-caused against the
actual v0.20.6 source, fixed, and committed (`0ddaa725c`):

1. Our `nanoid@3.3.18` CVE-2026-67213 leaf patch, installed directly into
   vite's `node_modules`, now fails npm's peer resolution — v0.20.6 bumped
   bundled `vite` to 8.3.0 (peer-requires `@vitejs/devtools@^0.7.1`) but
   still bundles `@vitejs/devtools@0.4.12` (the vendor's own internal
   mismatch). Fixed with `--legacy-peer-deps` scoped to that one install.
2. `patch_telegram_send_base_url.py`'s anchors no longer matched:
   upstream moved `_send_telegram` out of `tools/send_message_tool.py` into
   a new `tools/send_message_senders.py`, and extracted the old inline
   proxy-fallback `Bot()` construction into a shared `_telegram_bot(token)`
   helper — independently converging on the same shape we were patching.
   Both call sites were also reformatted, and `_standalone_send` gained an
   unrelated `secret_scope` token-fallback that had to be preserved, not
   clobbered. Re-anchored against the real v0.20.6 source (extracted and
   diffed the candidate image directly).

**Third break stopped the bump:** `check-vendor-compat.sh`'s A2A JSON-RPC
smoke test (step 5 — POSTs a `GetTask` call to the candidate's inbound A2A
listener on `:9900`) times out with connection-refused. Confirmed via a
200-second manual poll (not a timing race — the port never opens). Root
cause traced partway: `plugins/platforms/a2a/tools.py::_a2a_tools_available()`
reads `cfg["platforms"]["a2a"]["enabled"]` via `hermes_cli.config.load_config_readonly()`,
and `"platforms"` **is** a recognized root key
(`hermes_cli/config.py:1055`) — but the vendor's own config loader silently
strips it from the persisted `config.yaml` on boot regardless of nesting
(tried both `gateway: platforms: a2a: ...` — the OLD shape, matching the
comments already in `check-vendor-compat.sh` — and bare top-level
`platforms: a2a: ...`; both got stripped). The exact new schema shape for
enabling A2A in v0.20.6 was not pinned down within this run's budget.

This affects only the compat check's own synthetic test config — A2A is
disabled in the real production template
(`docker/config/hermes/config.yaml.tmpl`) either way, so this is not a
production-facing regression, just an unresolved unknown blocking the
version-bump gate. Hermes stays pinned at the current digest
(`sha256:68e15ae2...`, v0.20.1).

**Net effect:** the vendor pin didn't move, but the OS-package layer inside
the Hermes image (Debian base + `apt upgrade`) still gets refreshed by the
plain rebuild in §5 below, so this does not block CVE remediation at the
base-image level — only the Hermes-agent-specific CVE surface tied
specifically to versions between v0.20.1 and v0.20.6.

## 6. Incident during apply: exit 50, manual recovery required

Worth reporting in full rather than glossing over — the run was not clean
end to end.

1. **First apply attempt** (before the profile fix, §1 item 4) reported PASS
   having only rebuilt 3 of 5 required containers, undetected until compose
   config was checked directly.
2. **Second attempt** (after the profile fix) correctly built all 5 images,
   but the `hermes` bug (§1 item 5) made `docker compose up` fail. The
   script's own automatic rollback fired — and **the rollback itself failed**
   (exit 50, the script's own worst-case code: "STACK MAY BE DEGRADED, MANUAL
   INTERVENTION REQUIRED"), because rollback hit the exact same
   compose-can't-manage-hermes problem trying to force-recreate everything.
   At this point `agentshroud-marvin-gateway` and `agentshroud-docker-socket-proxy`
   were stuck in `created` (never started) — dev was genuinely down for a few
   minutes.
3. **Separately**, the rollback's `git restore --source=<baseline> --staged
   --worktree -- .` (fired during step 2) restored the INDEX as well as the
   working tree to a baseline captured before most of today's fixes. A
   follow-up commit that only intentionally staged one new file ended up
   committing the whole (stale) index, silently reverting four files back to
   pre-fix content — caught by reviewing `git show --stat` on that commit
   before trusting it, not by the tooling. Restored verbatim, documented, and
   committed (`0cdf3276b`).
4. **Manual recovery**, in order: sourced `docker/versions.env` into the real
   shell (the raw `docker-compose up` I ran directly was missing it — my own
   mistake, not the script's), brought up everything except `hermes` via
   `--profile voice`, then deployed `hermes` correctly via `scripts/asb up
   hermes` (the tool that already handles its secrets correctly) —
   `post-deploy-check.sh`: 9/9 checks passed. Stack fully healthy again
   before continuing.
5. **Fixed the actual bug** (§1 item 5) so the script doesn't attempt this
   again, re-baselined, and re-ran the full `apply` → `verify` cycle clean —
   see §7.

Lesson recorded in the fix commit: re-run `--phase baseline` immediately
before each `--phase apply` attempt, not once at the start of a session with
multiple commits in between — a stale baseline turns a failed build's
rollback into an unintended revert of everything committed since.
