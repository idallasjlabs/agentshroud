## 3. Colima socket-forward death — recurred live, during this session

Confirmed firsthand, not inferred from logs:

```
$ timeout 15 docker ps ...        # exit=124 (timeout)
$ timeout 10 colima ssh -- echo ok
ok                                  # exit=0 — VM up, SSH mux fine, docker.sock forward dead
```

This is the exact failure signature documented in `docker/scripts/colima-health-check.sh`
lines 187-229 and in the last 4+ Sunday reports: the SSH-mux stays alive,
`colima status` reports running, but the docker socket forward is dead. The
in-flight apply build (§0) stalled at Dockerfile step 54/125
(`RUN mkdir -p /var/log/falco && chown ...` — a sub-second command) for 12+
minutes with no progress, consistent with the daemon connection dying mid-build.

The `*/5 * * * *` cron self-heal (`docker/scripts/colima-health-check.sh`,
landed in PRs #459/#461/#463 this week) is installed and active
(`crontab -l` confirms it), and reported 0 failures / all healthy as recently
as 07:05:14 UTC (i.e. ~2-3 minutes before the socket died again under this
build's load) — so the fixes shipped this week reduced neither the frequency
nor the mechanism of the underlying failure, only detection latency. **This
is the same root cause flagged as item 1 in `reports/upgrade-2026-09-22.md`,
now confirmed recurring a 6th+ time.** Recommend the dedicated Lima/vsock
investigation that report already called for — patching the symptom
(self-heal) has not moved the needle on the cause.

**Resolution taken this session:** the orphaned build (§0) sat motionless on
the same sub-second Dockerfile step (54/125) for 15+ minutes with zero
progress while this session's own `docker ps` calls independently timed out
— conclusive evidence the build's specific daemon connection was dead beyond
any chance of self-recovery (the 5-min cron self-heal never fired because its
own fresh `docker info`/`docker inspect` calls kept succeeding — a *new*
connection, unlike the build's stuck long-lived one). The cron's own detection
logic is therefore blind to this exact variant of the failure. Terminated the
zombie process tree (`kill -TERM/-KILL` on PIDs 68195/68198; a second orphan,
76346, also spawned around 03:07 by the persistent `agentshroud-dev` session
and died on its own once Colima went down) and performed the same
stop-then-start repair `docker/scripts/colima-health-check.sh` performs:

```
$ colima stop            # clean shutdown, ~40s
$ colima start --cpu 8 --memory 10 --disk 120 --network-address   # ~40s, matches the single-source-of-truth flags in colima-health-check.sh:75
$ docker ps              # now responds — all 7 dev containers restarted "Up 7 seconds"
```

Also found and fixed a stale `DOCKER_HOST=unix:///Users/agentshroud-bot/.colima/docker.sock`
in this shell (missing the `/default/` path segment `colima-health-check.sh`'s
`resolve_docker_host()` uses) — pointing at a socket that doesn't exist after
a fresh start. Exported the correct path for the remainder of this session.

**New finding for follow-up:** the cron self-heal only checks `docker info`/
`docker inspect`/`docker exec`, none of which detect a *build-specific* dead
stream — a long-running `docker build` can hang indefinitely while the health
check reports everything green. The self-heal needs either a build-progress
watchdog or for callers (this apply script included) to bound their own build
step with a timeout rather than relying on the health check to notice.
