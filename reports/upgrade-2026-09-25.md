## §1 Root-cause: dev run was crashing instantly, every attempt, on a real bug

`--phase all` was launched and, like the 03:00 attempt, died within ~16s of
"scan: applying accepted-risk register" — before ANY per-image scan result
was logged. This is not a CVE gate failure (`dev-result-2026-09-25.json` at
that point showed `enforced:false`, and no `--max-critical` was passed) —
exit code was a bare **1**, not one of the script's documented `die` codes
(10/20/30/40/50). Isolated `--phase scan` alone reproduced it identically
(exit 1, same ~15s crash window).

`bash -x` traced it precisely: `scripts/lib/sunday-scan.sh` computes
per-image CRITICAL/HIGH counts as
`crit="$(printf '%s' "$out" | grep -o '"Severity": *"CRITICAL"' | wc -l | tr -d ' ')"`.
`grep -o` exits 1 on zero matches. This script (and its caller,
`sunday-upgrade-apply.sh`) run under `set -euo pipefail`, so a genuinely
**clean** image (0 CRITICAL findings) made `grep` return 1, `pipefail`
propagated that through the pipeline, and `set -e` killed the entire script
on the spot — no `die()` message, no warning, just instant death and a FAIL
handoff written by the EXIT trap. The trace showed `crit=0` computed
correctly, then the very next lines were the EXIT trap firing — `high=`
never even ran.

**This bug is newly latent, not old**: it can only fire when an image scans
to exactly 0 CRITICAL (or 0 HIGH), which only became reachable after #478
(2026-09-24, accepted-risk register) started filtering some images down to
zero. Before that, every image had ≥1 unfiltered CRITICAL, `grep -o` always
matched, and the bug never fired. This is almost certainly the direct cause
of the 03:00 attempt's silent death today, and plausibly a contributor to
recent days' failures once the register started landing.

**Fix** (`067c362c63`, on this branch): wrapped both greps in
`{ grep ... || true; }` so a legitimate zero-match result doesn't fail the
pipeline. Verified: `--phase scan` alone now exits 0 —

```
[apply 05:09:04] scan: agentshroud-gateway:1.7.0 -> 0 CRITICAL / 146 HIGH
[apply 05:09:28] scan: agentshroud-openclaw:1.7.0 -> 0 CRITICAL / 167 HIGH
[apply 05:09:51] scan: agentshroud/hermes:1.7.0 -> 2 CRITICAL / 390 HIGH
[apply 05:09:52] scan: wrote .../scan.json (total CRITICAL: 2, images scanned: 3, scans FAILED: 0)
[apply 05:09:52] scan: PASS (3 image(s) scanned)
```

Per CLAUDE.md §0.05 ("needing a code change is not grounds to skip a bump —
make the change, test it, ship it"), this was fixed and shipped on this run's
branch rather than reported as BLOCKED.

Root cause, from the captured build log: the `falcoctl-builder` stage in

oras-go/v2@v2.6.2 or sigstore/fulcio@v1.8.6 are the likely candidates) now
requires Go ≥1.27, and `GOTOOLCHAIN=local` (deliberate — no network
toolchain fetch mid-build, see the file's own `slsa-builder` comment)
refuses to auto-fetch it. PR #480 bumped the falcoctl version but not the
builder's Go base, so the gateway image has been unbuildable since that
merge (04:58 ET) — this run is what surfaced it.

**Fix** (`42d01938c0`): bumped only the `falcoctl-builder` stage to
`golang:1.27-trixie@sha256:433790e5...` (digest-pinned). Left
`slsa-builder`/`cosign-builder`/`docker-cli-builder` on 1.26-trixie — they
build clean with their own smaller forced-dep sets, no reason to move them.
Verified in isolation: `docker build --target falcoctl-builder -f
gateway/Dockerfile .` → `Successfully built ...`, `/out-falcoctl version` →
`Client Version: 0.14.2`.
