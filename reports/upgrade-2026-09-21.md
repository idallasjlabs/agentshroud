## 8b. Cross-session catch: browserslist build break, caught by prod before it shipped

Mid-run, prod (a separate session on the `ijefferson.admin` account, via the
`agentshroud-dev` coordination session) reported that it had test-built
`chore/upgrade-2026-09-20` independently and hit a real failure:

```
npm error code ETARGET
npm error notarget No matching version found for browserslist@4.29.0
with a date before 9/7/2026
```

**Root cause**: the Hermes vendor's own base image ships `/opt/hermes/.npmrc`
with `min-release-age=14` (refuses any npm package published <14 days ago)
plus an explicit allowlist. `nanoid@3.3.19` is on that allowlist (installs
fine); `browserslist@4.29.0` (published 2026-09-15, confirmed via the npm
registry's `time` metadata — only 6 days before this build) is not, and fails
the gate. This came from an earlier same-day pass bumping browserslist to
npm's literal latest instead of the oldest version that actually fixes the
two relevant CVEs (4.28.7, published 2026-07-21, already contains both
CVE-2026-73088 and CVE-2026-73089 per this file's own pre-existing comment).

**Fixed and pushed this run — but the first attempt at the fix repeated the
exact defect CLAUDE.md §0.0 is about.** Commit `ea87ef13d3`'s subject said
"revert browserslist to 4.28.7" and its comment block correctly explained
why, and it was pushed — every signal that normally means "done." But the
actual `RUN npm install ... browserslist@4.29.0` line was never touched.
`agentshroud-dev` caught it by running
`git show HEAD:<file> | grep browserslist | grep -v '^\s*#'` against the
pushed commit — i.e., checking the line that executes rather than trusting
the commit narrative — and it still printed `4.29.0`. Corrected in commit
`7eaf459b03` (the ONLY change: `4.29.0` -> `4.28.7` on the actual `RUN`
line), re-verified with the same grep before telling anyone it was fixed,
pushed. This is now applied retroactively to every other version claim in
this report too — §8's "already latest / upgraded" table entries were each
re-checked against `git show HEAD:<file>` for the literal pinned value, not
against the commit message that introduced them (see the verification block
immediately below).

Verified no equivalent freshness gate exists on the Python/uv side of
the same base image (no `pip.conf`/`uv.toml` found), so the tornado 6.5.10
bump (§9 item, commit `553fb8affb`) is not at risk of the same failure class.
